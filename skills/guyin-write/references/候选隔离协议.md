# 候选隔离协议（D2 已实现接口；整章多候选为冷路径——仅作者显式启用时读）

> 热路径入口见 [SKILL.md](../SKILL.md)「写章循环」：**单稿也先隔离**——候选只在项目隔离工作区 `.guyin/work/{run_id}/` 内产生与演练，`guyin-tracking-commit.py publish` 是唯一正式化入口（日更/大修/去味共用）。整章多候选（A/B 对照）默认不启用：作者显式要求、且事先声明候选数与费用上限时，才在同一隔离机制上开多个 run_id 平行演练（同预算比较，不给新法更多抽卡机会；不默认前三章或 L3 各产 2-3 整章——先按一次明确修订假说产一版，与保留原稿比较）。

## 隔离工作区（已实现）

- 每个发布运行一个 run_id：候选正文、逐章事务、只读输入快照、审读/检查记录、run.json 全部落在 `.guyin/work/{run_id}/` 内，不进正式 `正文/` 扫描范围。旧设计的 `正文/_candidates/` 已废弃——候选任何时候都不出现在正式正文目录。
- 多候选时一候选一 run_id，均从**同一正式正文/追踪/指纹基线**出发；依赖提交态的全链检查只在工作区内对候选执行；失败候选也留记录，不删。
- **不共享正式追踪文件**——永不复制候选整棵追踪树覆盖正式项目；追踪推进只能由 publish 的机械步骤做。

## 同序组织

仍用 beat-writer 时，编排层为每个候选（run_id）独立顺序组织各 beat（单 beat agent 不写整章）；更大场景单元另作等预算试验，不在本轮暗换架构。

## 发布事务（已实现，publish 串行状态机）

选定候选后编排层产出发布清单，交 `guyin-tracking-commit.py publish --project <书根> --input <清单.json>`，不再手工执行「存档→正文→追踪→指纹」双命令：

1. **prepared**（全量校验通过前不动正式文件）：候选必须在本 run 的工作区内；destination 为 `正文/第0*N章*.md` 且章号一致；append 目标不得存在、revision 目标必须存在（旧稿先自动存档 `正文/_archive/第NNN章_发布前存档_时间戳.md`）；基线清单逐文件哈希/目录成员核对；事务 dry-run 规范化；审读结论非空且全部证据文件内容逐字含候选 hash12；待审台账无未决阻断。
2. prepared 固化全部输入哈希后机械推进：`prose_written`（原子安装）→ `tracking_committed`（现行唯一事务通道）→ `fingerprint_committed`（持锁调 `guyin-check-repetition.js --commit --under-lock`）→ `complete`（正文/state/视图/指纹库对 journal 终验+再过一次未决门）。
3. 中断（exit 3 或进程死亡）一律 `guyin-tracking-commit.py recover --project <书根>`：绑定同 run_id 与已固化版本续跑，追踪不重复 append，指纹失败只补指纹，库损坏走 `--recover-library` 隔离+基线重放+复检（复检不冒充通过），超出基线的外部变化停用户裁决、禁回滚。
4. 胜出发布后正文、摘要、追踪、指纹同版；非 complete 的 `_publication.json` 会被 `check/commit/backfill` 与 setup hook 同时拦截，书无法带着悬置发布继续写。

接口与恢复语义见 [tracking-transaction.md](consult/tracking-transaction.md)「发布契约」节。

## 裁决纪律

- 无净收益不默认覆盖原稿，纯品质润色保留旧版（放弃的 run 留在工作区即可，正式状态零变化）。
- 旧版存在必须修复的事实/安全契约错误时，即使阅读偏好平局仍须单独处理（不用「保旧稿」掩盖硬错误）。
- 达到事先预算或没有新修订假说时停，不机械重写第十几版。

## 验证状态

- **已实现并测试**（`tests/run-tests.js` D2 块）：未选候选不进正式状态、prepared 任一拒绝项命中时正文/追踪/发布文件零变化、正式基线变化拒绝覆盖、append/revision 目标状态校验、四阶段中断 exit3→recover 续跑 complete、tracking 后崩溃不重章、损坏指纹库受保护恢复、锁互斥（活 pid/死 pid/--under-lock）、hook 发布门。
- 仍属冷路径编排、未做端到端整章验证的是「多 run_id 平行演练 + 等预算裁决」的**编排层流程**（beat 分组、候选间裁决记录格式）；其下层发布/隔离/恢复机械契约已可用，不因此回退为手工发布。
