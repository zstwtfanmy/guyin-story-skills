# 候选隔离协议（drafts 版本化 + publish 唯一正式化）

> 2026-09 v4：候选正文只在项目隔离工作区 `.guyin/work/{run_id}/` 内产生；当前会话自主执笔，不再有执行层 agent。
> 热路径顺序与恢复纪律见 [SKILL.md](../SKILL.md)；进度/指针/哈希由 `scripts/guyin-author-session.py` 管理（§4.3/§4.4）。整章多候选（A/B 对照）默认不启用：仅用户显式要求并事先声明候选数与费用上限时，才在独立 run_id 书根上平行试验（§7.4），等预算比较，不给更多抽卡机会。

## 工作区结构（已实现）

- 每个 run 一个 run_id：`input.json`（冻结授权/锁/事实/profile/篇幅）、`author-session.json`（唯一进度权威）、`drafts/vNNNN.md`（候选版本，只含正文）、`review.md`、`transaction.json`、`check-evidence.json`、`plan-patch.json`、`publication/`（发布预演字节）。
- 已登记候选版本永不原位改写、不删除：修订另存新版本，先切 session 指针再发布；未被登记的孤立稿保留在盘上供核查，不自动当定稿。
- 候选任何时候都不进正式 `正文/`；旧 `正文/_candidates/` 设计已废弃。不复制追踪树覆盖正式项目——追踪推进只能由 publish 机械步骤做。
- 多候选=多个 run_id（或 §7.4 的独立书根 A/C），从同一正式基线出发；失败候选也留记录。

## 选定与发布

- 选稿/发布是两种授权，分别记录在 input.authorization，换稿后 selected-candidate 授权立即失效。
- 选定候选后准备发布清单（v2：含 `author_input`、`candidate_checks`），ready 先 `tracking-commit.py preview`（纯内存预演，授权可为 null，不写正式正文/追踪），再 `publish`。
- publish 五阶段状态机（prepared→prose_written→tracking_committed→fingerprint_committed→complete）与 recover 语义见 [tracking-transaction.md](consult/tracking-transaction.md)「发布契约」节；中断只走 recover，绑同 run_id，不重 append、不认混合状态。

## 裁决纪律

- 无净收益不覆盖原稿，纯润色保留旧版；放弃的版本留在 drafts，正式状态零变化。
- 旧版存在必须修复的事实/安全错误时，阅读偏好平局仍须处理，不用「保旧稿」掩盖硬错误。
- 达到事先预算或没有新修订假说时停。
