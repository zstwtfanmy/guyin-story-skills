# 框架整改实施任务书：让生成内容真正值得读

> 基线：2026-09-16，guyin-skills `e2a75fa`。状态：**实施规格，尚未实施，作品效果未验证。**
> 本文从《框架总诊断_正确性机器为何天然无趣》中提取并校正执行方案，原文保留供追溯；实施不必重读历史争论。
> 本次只交付本文。后续实施仅改框架、模板与仓内测试；不擅改外部小说、已批准细纲或用户配置。项目部署更新另行确认。

## 1. 整改目标与交付判定

**唯一产品目标：让用户读新生成的正文时，关心具体人物，获得本题材承诺的阅读体验，并愿意继续读；这种效果能够跨连续章节积累。**

《隐杀》《晚明》《铁血残明》是质量参照，不是同一套文风模板。不得把脚本通过、措辞精致、设定严密或“像某位作者”当作目标完成。

必须同时解决四件事：

| 整改目标 | 必须改变的生产行为 | 不合格的替代交付 |
|---|---|---|
| 内容本身值得写 | 规划时选择有具体人物意图、处境和阅读价值的场景；无价值回规划 | 增加“有趣、鲜活、有灵魂”字段 |
| 有价值的设计写得出来 | 给执笔者必要因果与原文，连续完成场景，保留表达判断权 | 只把“填空写手”改名为“作家” |
| 审读能改善而不磨平 | 完整阅读后按根因修订；没有净收益不覆盖 | 报警减少、逐项补齐反应句 |
| 改变能留到下一章 | 已发生的关系、资源、认知与承诺变化进入状态，并被下章实际使用 | 摘要写了三件事，但人物又恢复原状 |

**审核结论：完整实施具备改善吸引力的针对性，但不能提前保证解决。** 它能消除已核实的流程冲突；选材是否成立、模型能否兑现、读者是否愿读仍须验收。只做放权、减检查或换模型，不构成本次整改。

交付分开判：①工程闭环通过；②用户确认已测作品改善；③连续单元保持改善。没有②不得称“解决无吸引力”，没有③不得称“可持续”；跨题材能力只报告实际测过的范围。

## 2. 目标运行链：规划、创作、审读、发布只走这一条

```text
用户授权的写作任务 + 当前正式状态
  → 当前章设计：谁想做什么，处境为何值得读
  → 必要上下文：事实边界 + 场景意图 + 相关原文
  → 连续生成完整场景/章，保存隔离草稿
  → 全文初读，再核对因果与契约
  → 定向修订；失败回规划或暂停，不凑句子过关
  → 选定版本，隔离环境内完成摘要、状态和检查演练
  → 受控发布正文、追踪、指纹，核对同版
  → 将实际后果带入下一章；用户反馈反查最早失效层
```

书级选择负责方向，编排负责取材和边界，执笔负责表达，审读负责发现阅读损失，脚本负责可确定的检查与状态一致性。职责可以由同一模型承担，但不得将同会话自审称为独立初读。

### 2.1 规划契约：复用字段，删除重复剧本

权威定义仍放 `skills/guyin-write/references/细纲协议.md`。将原有重复栏目合并为以下四组，不新增一份并行大纲：

| 组 | 复用原字段，保留的内容 | 消费与退回条件 |
|---|---|---|
| 本章要交付什么 | 核心事件、阶段位置、读者承诺、收益归属、字数目标 | 编排选择场景，审读检查实际体验；只能说“推进剧情”则回规划 |
| 人为何这样行动 | 人物目标/关键选择、逻辑线、关系变化、视角/信息差 | 说明相关人物各自想要什么、知道什么、凭什么能做；配角只有“配合主角”的理由则重选行动 |
| 场景如何承接 | 按场景简述起点、意图、行动可能、前后变化及承接 | 执笔连续创作；不预写逐句动作，不要求每场反转、冲突或明确升降 |
| 哪些不能擅改 | 已发生事实、知情边界、明确保密项、用户锁定结果、确需逐字一致的世界内原话 | 核实硬契约；和前三组冲突时回编排，不编造补丁 |

必须删除普适的情绪次数、场景数、十多个节点配额、逐点字数配平、固定五段式、实体谜物式章尾要求；确为用户选择的书级约定除外。保留明确长度要求，但内容撑不起长度时修设计或请用户调整约定，禁止填水。

规划改为：当前章细化，后续约2—3章保留承接和后果，更远保留阶段方向。章数只是起点，不是检查门。既有获批细纲不自动重写，锁定结果仍有效；后果使后续计划不合理时提出调整，不把人物强拉回旧剧本。

**场景选择必须做的判断，不是新增打分表：**
- 人物为何此刻这么做，而不是作者需要这样？若重要配角坚持自身利益或认知，这一场还成立吗？
- 读者在这一场能经历什么：好奇、能力兑现、关系亲近、惊惧、幽默、生活滋味或别的明确体验？不是填情绪词，而是指出产生体验的处境与行动。
- 去掉这一场，会失去什么值得保留的体验、理解或后续条件？纯粹复述已知信息而无新作用，应删并或换设计；日常温度、余韵本身可以有价值。

卡壳时才比较2—3个“人物选择或局势后果不同”的简案；不能只换感官、比喻和开头句式。每场都强造障碍、反转或代价，同样判为模板化。

### 2.2 执笔契约：一份简报，三类权限

直接替换 `cards/写作卡.md` 及组装说明，沿用 `guyin-beat-writer` 名称，避免为改名增加路由迁移。

```text
【不可擅改】相关既定事实、知情/保密边界、锁定结果及来源。
【这一场】相关人物各自的意图与处境；需要成立的体验与承接。
【必要材料】相关前情原文、当前状态、连续声线锚；列明来源。
台词、动作细节、节奏、心理、幽默和局部走向由执笔决定，不能改动硬边界。
```

- beat只作节奏标签，不再等于独立调用、字数桶或逐拍验收单位。默认连续完成完整场景；承载得住时写整章；输出上限不足时按自然边界拆。
- 上一段100/300字只能当声线锚，不能替代因果前情。编排从角色状态、承诺与相关原文按需取材，不把全书和检查词表塞给写手。
- 无工具写手缺必要材料时返回“材料不足”控制结果，不伪装正文；编排补齐后继续。正常正文与控制结果分开处理，拒绝把诊断说明拼进成稿。
- 同章后续场景使用已选草稿中的变化作为临时上下文，不提前写正式追踪；废弃候选的变化不得混入另一候选。
- solo与subagent拥有相同创作权限。宿主、实际调用方式、模型与可见参数分开记录；不可见写“未知”，不以提示词“高温/零温”冒充实际参数。
- 删除默认峰值抽3—5稿、五感入口、固定丢弃前两项和逐beat语义问答。默认单稿；增加候选必须先约定数量与成本。

### 2.3 审读契约：先识别阅读失败，再决定改哪里

复用现有完整章审读，将 `自检卡` 改为场景/章级审读辅助，不再独立卡住每个beat。

1. **先全文初读**：哪里开始想读/不想读，期待什么，记住谁，哪里得到兑现；引用具体段落，可答“没感觉/不知道”。有独立上下文时只给正文、必要前文和读者定位，不给细纲、设计解释或自评。
2. **再核对设计与事实**：动机、能力依据、知情边界、收益和承接是否成立。人物反应和后果可以隐含或延迟，不要求动作后立即补反应句、后果句。
3. **只锁定当前主缺陷**：说明证据、修订假说、要保护的表达，再路由。

| 根因 | 路由 | 禁止动作 |
|---|---|---|
| 词句失真、重复、局部表达不清 | L1 段落修改 | 因句长或词频单独触发全文润色 |
| 设计有价值，场景表达未兑现 | L2 完整场景重写 | 把场景失败拆成多个补句任务 |
| 人物选择无由、事件无价值、承接失效 | L3 回章设计/中程规划，再写候选 | 先去AI味；改用户锁定结果而不确认 |
| 确认的事实/工程错误 | 定位源头修复并复检 | 以“更有味”豁免错误 |

默认一轮结构修订，必要时再一轮局部语言修订；这是可调整的成本上限，不保证两轮成功。改后重读完整受影响场景；涉及结构或跨场承接时重读整章。比较问题消除、新问题、表达损失和阅读偏好，允许平局、都差；没有新假说或净收益就停。

`guyin-review` 不论full/solo都不能省全文阅读；`guyin-deslop` 只处理已确认的表达问题，不靠报警下降验收。审读未完成或主要阅读失败未处置时，不标合格；用户若明示保留失败稿，记录“用户保留，质量未通过”，不改写成质量认证。

### 2.4 检查契约：取消“所有报警都阻塞”，不取消硬保护

不以正则执行稳定证明文学判断成立。所有检查结果在消费前统一为以下处置类别：

| `handling` | 含义 | 默认去向 |
|---|---|---|
| `hard` | 可确定的工程错误、明确硬约定违约，或语义核实后的事实违约 | 修复前阻止发布/续写 |
| `verify` | 可能剧透、知情越界、资产否定等，仍需上下文核实 | 带证据复核；不能排除硬契约风险则暂停 |
| `editorial` | 比例、句式、比喻、记忆度等观察与编辑建议 | 留审读记录，不因未“清零”阻止写作；确有主要阅读失败按2.3处置 |

**接口决定：**脚本保留原有规则ID与证据，逐规则补 `handling`；review保留S1—S4影响等级和原category，另给 `handling`，不要把两种severity硬拼成同一个枚举。每项处置绑定正文版本、位置/原文与理由。缺分类、非法值或解析失败报工具错误，不能默认降为建议。

主流程是唯一消费入口：`hard/verify`进待审台账；`editorial`进入审读记录，不再自动制造待审阻塞项。新增分类必须同步台账模板、解析器、hook与调用方，不只改输出标签。

待审台账保留原有列与六种处置名称（修复/豁免/契约修订/顺延/升级作者/不适用），新增“处置类别、正文版本、决定依据”列，按表头读取。其中“升级作者”是等待态而非结案；历史行一律保留，只有当前检查点范围与当前正文版本匹配的裁决才生效：
- `修复`须关联新版本及复检结果；`不适用`须有上下文理由，确认误报不占艺术豁免名额。
- `升级作者`只有对应用户的真实决定才能转结（改稿/保留/暂停，改稿落到其余处置）；“已裁决”字样只作线索，处置必须落进五种结案之一或显式暂停，无法对应具体用户决定不得解除。
- `契约修订/顺延/豁免`不得仅凭填词解除硬问题：须有相应授权、去向与适用边界。工程损坏、未完成发布、已发生事实的矛盾不能靠艺术豁免放行。
- 处置严格完整匹配；`未修复`、`修复中`、未知值均不能闭单。正文版本与当前版本不匹配的历史行只是记录，不自动阻止，也不冒充当前裁决——当前版本必须有自己的处置，且关联被其替代的旧行。
- 损坏数据行、缺列或读取失败报工具错误，不得被静默跳过；已部署写作项目缺台账、权限错误或损坏须报告并停靠，空项目由setup创建合法空表，非写作项目不误拦。
- 检查CLI：0=无阻断，1=存在未决阻断，2=执行/输入错误；hook按宿主协议将应拦结果映射为2。不要把所有exit 1解释为必须改正文。

### 2.5 状态契约：用当前真实接口，不造第二套文学数据库

已核查：运行脚本输出状态schema为7，事务输入schema为1；部署模板仍是旧字段。**不得按旧模板向 `context.open_threads` 写入。**字段来源以 `guyin-tracking-commit.py` 的规范化函数为准。

| 正文产生的持久后果 | 写入已有事务字段 | 下章消费者 |
|---|---|---|
| 人物关系、认知、目标、资源变化 | `character_snapshots` 的 `relationships/knowledge/goal/abilities_resources/state`，必要时角色级 `open_threads` | 当前角色卡与场景简报 |
| 必须承接的近期变化 | `delta.next_chapter_commitments` | 生成的 `context.next_chapter_commitments` → 下章设计 |
| 长期限制、可能断裂之处 | `context.long_term_constraints/continuity_risks` | 下章读盘与滚动规划 |
| 伏笔、事件事实、时间与场景变化 | 已有 `delta.foreshadow_changes/timeline_events/verdict_changes/evidence_changes/geo_changes/scene_changes` | 对应派生视图与事实核查 |
| 本章实际发生什么 | `delta.result` | 近章速记与章节金字塔；不能替代全文审读 |

摘要提取只能以最终候选正文为证据，不能把细纲意图记成事实。保护合法闲笔，不要求转正率或每件小物品成为伏笔；无持久影响的细节留在正文即可。

**修订旧章的状态时点：**角色快照与context按整份提交，不能只从修订候选提取——先取截至最新已写章的正式现态，仅并入修订章实际改变的变化，其余原样携带；重写第3章不得把第10章已提交的关系、目标或知识退回。提交后核对受影响后续章正文与新现态是否冲突，冲突登记待审，不静默改写。

**必须一并修复的接口问题：**`context.recent_chapters[].summary` 当前上限360 UTF-8字节，而摘要卡要求约300字；逐章记录硬上限3072字节。不能把完整审读报告塞入 `delta.result` 或直接追加到脚本生成的逐章文件。将 `delta.result` 定为简短事实速记，遵守现有限额；详细审读、版本、调用与成本写独立运行记录，重提交不能覆盖它。材料超限时选取当前必要事实，持久实体仍进对应状态字段，不静默丢掉因果。

### 2.6 发布契约：先隔离演练，再提交；中断可恢复

单稿也先隔离，不以开启多候选为前提。统一工作区为项目 `.guyin/work/{run_id}/`，不放正式 `正文/` 扫描范围。包含草稿、只读输入快照、隔离项目、审读/检查记录与 `run.json`；这不是新增故事设定层。

`run.json` 最小保存：运行ID、目标章/篇、基线清单及哈希、候选路径/哈希、审读模式与结论、修订记录、实际调用与预算、最终处置。基线清单覆盖本次读取的规划/设定、正式正文、追踪与指纹；文件新增或缺失也属于基线变化。审读和检查记录必须绑定候选哈希，改稿后对应结果失效。

依赖提交态的检查，使用隔离项目中的既有目录布局执行：写入候选 → 提取摘要及实体 → 在隔离项目提交追踪和指纹 → 跑完整章检。不得为了提前检查而污染正式状态，也不得整棵复制隔离追踪覆盖正式项目。

**实现决定：**扩展现有 `guyin-tracking-commit.py`，增加 `publish --project <root> --input <发布清单.json>` 与 `recover --project <root>`，复用现有commit能力；以上是待实现接口，当前不能执行。发布清单引用运行记录、最终正文、事务JSON、基线和检查证据，脚本校验路径与哈希后工作，不重新让模型摘要。

发布器维护 `追踪/_publication.json`，以项目级互斥、`expected_state_revision`及基线哈希防并发覆盖，依次推进：

```text
prepared → prose_written → tracking_committed → fingerprint_committed → complete
```

- 开始前重新校验授权范围、基线未变、候选未变、审读已完成、未决阻断为零；旧正文先存档，新章不要求无意义的旧稿备份。`prepared` 阶段先固化事务输入与全部预期产物哈希；此后推进只做机械工作，不重新提取摘要或语义改写。
- 指纹库与 `_publication.json` 一律经临时文件原子替换写入；commit、backfill、指纹写入与journal推进共享同一项目级互斥，不得提供“跳过journal”开关。
- 每一步记录实际产物哈希及状态修订号；只有正文、摘要、派生视图、指纹一致且最终检查通过，才写 `complete`。发布是可恢复的串行事务，不宣称跨文件原子。
- `check`、主流程续写预检、hook共同消费发布状态。非complete或损坏均阻断新发布/续写；无hook宿主在命令入口执行同一预检，不宣称能拦任意外部写盘。
- 恢复是持锁的内部校验路径：绑定同一run_id与版本，不再检查未决阻断、不越过已完成步骤；公共预检仍拦任何非complete。追踪已成功时不能再次append同章；指纹失败只补指纹，不重写正文。

- 现有追踪机制“权威JSON最后写、此前失败可用同事务重跑”继续保留；超出当前事务基线的变化必须停用户裁决，禁止强行回滚覆盖外部修改。
- 多候选、日更、大修与去味后的发布共用此入口；普通低层commit不能绕过未完成发布。多候选仍默认关闭。

## 5. 作品效果验收：能否解决无吸引力，以这里为准

### 5.1 首轮只检验一件事：正文是否更值得读

由用户更新实际技能/部署后选择新章：新书可看前三章；续写选包含起因、过程、兑现和余波的连续段。不要求重写旧章，不由实施者擅自生产验收小说。

用户先看正文，不先看框架的自我解释。只需表达“想/不想继续读”和具体位置；可补充记住谁、在等什么、哪里兑现、哪里像在完成任务。不是要求每章填满五项，也不是必须同时有笑点、反转、代价和名句。

- 用户认为仍无聊：**产品目标未通过**，即使工程全绿也不得宣布成功。
- 用户认为更好读：记录正文版本和具体改善，可称“该样本获用户接受”；没有对照不声称已证明因果。
- 再看一个完整连续单元：验证后果和人物关系能否积累，而不是开头漂亮后面空转。跨题材再测另一个差异明显的题材，未测不泛化。

需要同起点A/B时另取用户授权；模型、输入、预算和人工介入尽量一致，先约定候选数，失败稿也计成本。比较可平局或都差；不重抽到新框架胜出。

### 5.2 失败必须回到最早失效层

| 实际结果 | 首先回查 | 不接受的补救 |
|---|---|---|
| 设计就没有期待或生活趣味 | 选材、人物意图、具体处境、题材阅读回报 | 再加“鲜活、爆点、有灵魂”指令 |
| 设计有价值，正文却成报告 | 必要原文是否传到、粒度是否完整、模型表达能力 | 加狠话/物件/反应句，反复同稿抽卡 |
| 初稿有味，审后更平 | 对照哪次修改损失了什么及其触发规则 | 以少报警证明修改正确 |
| 单章好读，连续章节空转 | 持久后果是否入库并被规划消费 | 继续堆黄金三章技巧 |
| 只适合一种题材 | 题材约定、材料真实性、示例是否误导 | 把所有题材改成同一文风 |
| 同一失败没有新判断 | 保存版本和失败原因，交用户决定暂停或换假说 | 无限加规则、强迫用户补人生故事 |

## 6. 实施后的最终审核要求

**对主要已知问题的覆盖是有针对性的，对效果的保证不足，覆盖完整性仍待验证。** 本方案同时处理上游选材、表达权限、语义审读、返工净收益、跨章后果和部署生效，比“只放开写手”更接近真实创作链；但它不会自动补齐题材知识、作者判断与模型能力，也不排除存在尚未识别的失配。

实施方交付必须包含：实际修改文件与旧规则删除项、生产者到消费者的运行证据、测试结果/未测项、项目升级差异、同等任务成本、用户作品验收状态。允许结论为“工程已实现，质量未通过”；禁止用一份完善报告替代正文效果。

**停止线：用户持续不想读，就仍未解决问题。下一步应根据正文证据修正最早失败的环节，而不是再把任务书写漂亮一次。**
