## 〇、总判词与第四条根因

v3 报告核心诊断：三轮失效模式演进——v1 护栏缺失（执行率低）、v2 高保真传导（细纲 bug 1:1 落地）、**v3 过保真（细纲的元语言被执行成正文）**。框架侧把 v3 的 S1-S5 与 G1-G6 归并为一条新根因：

### 根因四：接口无契约（高保真管线的翻译层缺失）

07 修好了「细纲承诺必须兑现」，但没有规定**承诺以什么形态传递**。细纲里指令（「推理≤3步」「让小窦问一句」）与内容（人物说什么话）混排同层，执行层无从区分「这是什么」和「要写什么」，于是把指令本身写进了对白（S2 十处泄漏）；生成端产出结构化草稿（带 `## 声线锚` 小节、末尾「承接：第62章……」）直接落盘为终稿（S1 脚手架残留）；签名句没有归属登记，每章提前说出下一章的招牌句（S3 跨章剧透四处）；钩子引了一句细纲设计了、正文没人说过的话（S4 幽灵引语——执行偏差区三章全留空的直接后果）。

**架构判语（采报告 §一）**：细纲层与执行层之间需要显式接口契约——指令区与内容区分离、成稿结构与正文规范对齐、签名句有归属章登记、偏差有机械对账。本计划 K/V/R 三系就是补这四个接口件；Q 系是顺带追回一条**在 06 建制时意外丢失的老资产**（情绪节拍表，考古见 §二 Q 系）。

### 状态层欠账的机制面（G5 框架侧）

v3 实证：61-63 重写时 `_tracking-state.json` 停在 8/26，台账停在 8/28——**整个追踪提交步骤被跳过**。S1 预检（07 v1.2）只接在「写指定章/日更」场景的预检位，而重写 61-63 走的是**大修场景**，该场景路由行只写了「落盘后 tracking-commit 重提交」，既无预检也无章检链兜底——大修路径天然绕开全部状态门。这不是纪律问题，是**场景接线缺口**（V2 治）。

## 〇.5 追加分析一：上一轮修改为什么引入了本轮问题（v1.1，作者复核轮）

四代失效的演进不是「修错」，是同一个系统性质在每轮修复后的显影：**这条管线是无差别保真传导器——任何一层没有形态契约的东西，执行层把它原样传下去**。逐轮回放：

| 轮次        | 修复动作                         | 引入的新失效                            | 传导机理                                     |
| --------- | ---------------------------- | --------------------------------- | ---------------------------------------- |
| v1→v2     | 恢复护栏、补契约槽位                   | 细纲的 bug 1:1 落地（时序倒错）              | 管线保真了，但上游没有时序校验——垃圾进垃圾出                  |
| v2→v3     | 细纲加更多规范字段（时序自检/偏差槽/解密位）＋全链检查 | **十处指令入文 + 脚手架落盘 + 跨章剧透**         | 规范字段本身也是文本——执行层不区分「这是什么」和「要写什么」，把规范当内容写了 |
| v2→v3（并行） | 检查链接入写章循环/写指定章/日更            | v3 会话**整个检查链没跑**（tracking 停 8/26） | 大修场景没接线——门存在≠门在路径上                       |

三条结构性教训（本计划的防复织依据）：

1. **修复施加层 ≠ 失效发生层**。07 的 P 系把规范继续加在细纲（施加层），而失效发生在「细纲→卡→正文」的翻译层。v3 证明：给上游加更多字，等于给无差别传导器加更多被传导物。K 系全部施加在接口（指令区隔离/成稿形态门/签名句归属表），不再往细纲内容通道里塞东西——细纲本轮新增的两行（情绪落点/指令区）都是**通道声明**而非指令文本本身。
2. **门存在 ≠ 门在路径上**。检查脚本只接了两个场景，重写走大修路径整链旁路。V2 的结论：接线完整性要按「场景 × 管线点位」矩阵审，不是按脚本逐个审。
3. **输出形态从未进契约**。管线契约止于内容（写了什么），从未约束形态（以什么样子落盘）——执行层返回结构化草稿就落结构化草稿。K3 补的就是这个空契约。

### 追加分析二：还有哪些问题没暴露（残差清单）

按同一传导机理推演，v3 报告没照到、但同病因的隐患（分「本轮已接线」与「接受残差」）：

**本轮已接线：**

* **细纲增重→注意力稀释→承诺掉落**（S5 ch62 塌方的另一解释：细纲每轮加字段，编排层注意力被元信息挤占）。处置：指令区 ≤5 行软上限写进协议（K1）；Q1/K1/V2 合计净增约 150 字后 SKILL.md 立即重锁预算（5420），细纲字段数此后**封顶不加**——下一轮再想加字段，先删一个等量旧字段（本文件作为此纪律的登记处）。

* **大修路径旁路面比 tracking 更大**（预检/章检/落盘门全不在路径上）。处置：V2 大修行接「章检链同跑 + 落盘前后 check」。

* **幽灵引语的检测盲区**：S4 只能查钩子行**已写明引语**的形态；钩子行不写引语时（如只写实体），引语是否伪造无机械判据。接受为走查残差（review 语义复评）。

**接受残差（显式登记，不修）：**

* **卡片通道不可审计**（docs/06 通道 3 既有结论）：写作卡不留档，事后无法核查「必须发生里当时装了什么」。K3 词表是汇侧兜底而非源侧审计——修复需要卡片归档机制，其内存成本远大于收益，维持不修。

* **solo 降级时自审盲区**：编排层 fallback 扮演执行层时，写与查同一注意力。既有缓解是确定性脚本（机械检查不随注意力衰减），这也是 K3/R1 全部走脚本而非走纪律的原因。

* **未声明签名句的提前释放**：未来章细纲未出时，K2 查不到对它的剧透。三查③人工走查兜底（协议已写明边界）。

### 追加分析三：架构统筹声明——为什么这不是盲叠（作者问题 2 的正面回答）

四代补丁（05/06/07/08）累计 30+ 检查脚本后，「再叠加逻辑」的担忧成立的前提是：新补丁与新失效模式同构。逐项核对本轮 10 项与既有 30 项的关系：

**防叠加四不变式（本轮全部遵守，也是此后验收新补丁的准入线）：**

1. **只挂既有点位，不新增阶段**：新检查全部接在已有管线点位（落盘门/章检链第 7 步/拼章第 4 步/tracking 提交尾部），零新流程阶段——流程图没有变复杂，变的只是点位上的门多了三个。
2. **一个失效模式一个主防线 + 至多一个兜底，禁第三层**：S1→K3（主）；S2→K1（源头）+K3（汇侧词表）；S3→K2；S4→R1；时滞→V2。无任何模式有第三层防御。
3. **机制归框架，词表归项目**：K3 词表只收跨书通用工序词（案卷/卷宗白名单内建），书特定泄漏词走项目黑名单通道——框架不替任何一本书养词表（06 同款决策）。
4. **advisory 起步，验证后升档**：K2/K3 词表/R1/Q1b 全部 advisory 起步（P1/O2 先例），blocking 仅限无歧义结构判据（多标题/承接段）。误报通过豁免台账消化并可复核。

**冗余核对（本轮新检查 vs 既有脚本，确认无重叠防御）**：strip-carryover 与 outline-copy 形态相近但判据不同（结构存在 vs 16 字连续誊抄），前者 blocking 后者 advisory，交叉报警是分诊信号不是冗余；outline-anchor-missing 与 outline-copy 方向相反（该抄没抄 vs 不该抄抄了）；K2 与 P3 唯一解密位互补（P3 管批内单点声明，K2 管跨章排他）。**反向核对（哪些旧防线本可拦住 v3 却没拦）**：outline-copy 本可拦「承接段」——但 v3 会话没跑章检链（V2 缺口的实证），不是防线冗余是路径缺口。

**如果将来要收缩而非扩张**：K3 成稿剥离门是唯一「形态」门，其余全是「内容」门——若某天管线稳定到执行层永不返回脚手架，K3 是第一个可降级为 advisory 的门。此为 08 的可逆性声明。

## 一、两个前置判定（回作者问题 3、问题 4）

### 1.1 执行偏差区：是设计缺陷，修法是翻转供给侧（R1）

**判定：是设计缺陷**，且 v3 已付出代价（S4 幽灵引语）。三个结构性问题：

| 缺陷        | 证据                                                               | 后果                       |
| --------- | ---------------------------------------------------------------- | ------------------------ |
| **无工具供给** | 「回填」= 手工通读比对细纲与正文的语义劳动，零脚本支持；tracking-commit 只有缺区 stderr 提醒（不阻断） | 长会话软步骤必被跳过——v3 三章偏差区全部留空 |
| **无消费端**  | 回填了也没人读：写作卡不含它、章检不校验它、下一批补纲读盘只读字段不读偏差区                           | 信息回流闭环断裂——回填成本付了却换不回任何防御 |
| **时机错位**  | 设计挂在第 6 步「追踪提交前」，该步注意力在实体登记（chapter\_summaries/evidence/geo）     | 偏差比对与实体登记抢同一个注意力窗口，被挤掉   |

**替换方案（R1）**：不做「修补回填纪律」，把偏差区从「作者凭空手写」翻转为「**检测报告生成 + 编排层裁决落盘**」——机械检测把「细纲与正文哪里不一致」找出来，人只做「修 or 认」的裁决。细节见 §二 R1。

**裁决自动化（v1.1 补，作者问题 4 的回答）**——「框架稳定化后人生成过程中无法参与裁决」这个判断**成立一半，且成立的那一半恰恰不是问题**：

* **成立的一半**：全自动日更/回炉场景确实没人守着做「修 or 认」。但现行框架里人本来就只在豁免时进场（改写卡通道是自动的，06 不变式 4 只拦「自动删/自动保留」）——R1 若把全部偏差路由给待审，才会制造出「等人裁决」的新瓶颈。

* **不成立的一半**：裁决的本质不是审美判断，是**契约优先级**。细纲是契约（07 确立的权威层），偏差发生时默认答案已定：正文欠契约的 → 修；修不动或代价更高的 → 修契约（登记偏差）。真正需要人的只有例外情形。所以方案不是「让 AI 学会判断」，是**把默认路径做成无需判断**。

**自动化裁决规则（已写进细纲协议「执行偏差区哲学」段）**：

1. **默认修**：检测到偏差（锚句未落地/引语不匹配/术语缺失）→ 走既有改写卡 L1 通道（自动，一次）；
2. **修不成则认**：L1 修复失败或复检仍有偏差 → 登记偏差区（契约修订：变体注明措辞、未落实写顺延章号）——**登记本身就是裁决**，契约即时生效，下批细纲读盘自然继承；
3. **仅三种情形升级作者**：① blocking 级偏差修复失败；② 偏差触及契约风险/资产档位字段（已有作者门）；③ 同一报警二次复发（防修复震荡）。
4. **唯一禁区**：无偏差无声消失——每条检测终态必居其一（修复/修订/顺延登记/升级），这就是 tracking-commit 校验「未落实必含章号」的语义。

该设计保持不变式 4 完整：自动路径只有「修文」（非删除）与「记账」（非湮灭），作者批后复盘仍可从偏差区逆向翻案。

### 1.2 情绪节拍表：真缺失，非已覆盖，且是三层链路断裂（Q1）

**git 考古结论（全历史** **`git log -S`** **核验）**：

1. 「情绪节拍表（每章至少三次情绪落点）」**从未存在于框架任何模板/协议**。全部历史命中只有两处：`tests/fixtures/ch36-细纲_修复版定性.md:27` 与 `ch36-细纲_档位冲突.md:26`——它们是 v0.5.0（commit f384179）从《白银案录》项目实际细纲收编的黄金样本。即：**节拍表是项目侧实践，不是框架资产**。
2. docs/06 建细纲协议时以 ch36 fixture 为基底提炼字段，收录了「目标情绪」「复沓锚句」「人心节拍」等行，**唯独漏了情绪节拍表**——06 全文检索「情绪节拍」零命中。成因：缺陷驱动的整改只收集与缺陷相关的字段（钩子/字数/多线/锚句/档位），ch36 的优点不在收集范围。这是**意外遗漏，不是有意裁剪**。
3. 追查发现断点比预想深一层：**写作卡模板没有** **`{{情绪目标}}`** **槽位**。cards/README.md 取数表第 36 行有条目（`{{情绪目标}} | 细纲标注 | 一个词`），但 [写作卡.md](../skills/guyin-write/cards/写作卡.md) 模板（背景/前文/必须发生/禁止/范文/感官入口）无对应槽——**执行层写 beat 时根本不知道本章本 beat 的情绪目标**，情绪完全靠「必须发生」的事件结构 + 范文手感隐式传导。

**覆盖性核对（现有字段是否顶替了节拍表）**：目标情绪行只管章级起终点；切 beat「标注情绪目标」是编排层内存动作、依据仅章级一行；情节点功能标签（密/疏）是节奏维度不是情绪维度；J2 管字数均质；Muse/发散卡只管峰值 beat。**结论：未被覆盖，v1-v3 三代细纲正文全裸奔**。实证伤害：ch62 塌方 1864 字 + 情绪平（无节拍表 = 情绪欠账在写前不可见、写后不可查）。

**链路三断点与修法**：细纲层（节拍表丢 → Q1a 字段回归）→ 卡片层（无情绪槽 → Q1c 模板补槽，顺带修复取数表失配）→ 槽位门（Q1b advisory 出声）。检查层诚实声明：情绪交付质量不可机械判（语义），走自检卡既有 Q7 事件交付 + review 语义复评，不做假机械化。

## 二、方案明细（10 项）

### K 系：接口契约（治 S1/S2/S3 —— v3 三类 S 级硬伤的直接成因）

**K1｜细纲「写作指令区」**（落点：`references/细纲协议.md` 模板 + `cards/README.md` 组装纪律；治 G1/S2，报告定调最高优先级）

* 协议模板在「结尾设定和钩子」与「执行偏差」之间增设区块（区推荐存在、值可「无」——比照执行偏差区哲学，但**不设槽位硬门**：指令不是每章都有，硬门会逼出空转）：

  ```
  #### 写作指令（本区内容禁止以任何形式进入正文）
  - 术语锚点执行方式：{勘合首现 → 谁问、谁答一句}
  - 推理与落位约束：{≤3步、第3步落锚句、锚句落点、收束不复用上一章收束位}
  - 比喻域/禁令：{本章比喻域约束、其他就近禁令}
  ```

* **消费规则（写进 cards/README 组装纪律，新加一条）**：指令区内容**永不进** **`{{必须发生}}`**（那是内容通道）；可提炼为 `{{禁止}}`（如「禁写步数/流程指令」）或卡尾复述。指令区是「怎么执行」，`必须发生` 是「发生什么」——两类混排正是 v3 十处泄漏（对白里出现「推理≤3步，已经到第三步」「勘合首次出现，让小窦问一句」）的生成机理。

* 机械边界诚实声明：指令泄漏不可全机械化（指令措辞自由），K3 词表拦高频形态（推理≤/执行方式/承接第），其余靠组装纪律 + review。

* 与 W3（工艺词括注翻译纪律）的关系：W3 管叙述层字段里的工艺词，K1 管执行指令的收纳位——指令不再散落在内容字段里，两者合起来把「元语言」从内容通道里清出去。

**K2｜时序自检扩三查 + 签名句归属机械检查**（落点：`references/细纲协议.md` 时序自检行扩容 + `guyin-check-outline-deliver.js` 加第四条检查；治 G2/S3）

* 协议时序自检行扩为三查（模板行更新）：

  ```
  - 时序自检：①章内时间轴走查 □ ②插叙显式标注 □ ③跨章签名句归属核对 □（本章锚句/招牌句/核心证据是否已在更早章被任何角色说出；本章是否提前说出后章细纲声明的锚句）
  ```

* **签名句归属 = 细纲字段本身，不建新文件**（决策点 ③）：报告 §五 G2 建议的「签名句归属小表」（章｜锚句｜归属）实际就是各章细纲「复沓锚句」字段 + 章尾钩子引语的聚合视图——细纲文件即登记表，归属即章号，写前查写后核交给脚本，不新增项目侧文件与登记开销（报告 §八风险表自己也在担心「归属表变成新开销」）。

* **机械检查** **`outline-signature-preempted`（advisory，加进 outline-deliver）**：输入目录时对全批做交叉核对——任一章正文包含**其他章**细纲声明的签名句 → 报警并标注方向（提前释放/归属被抢）。签名句提取启发式：锚句行剥落点前缀（`点N：`）、钩子行取引号语（「…」/“…”），长度 ≥6 字才入表（短句如「留着。」会误报噪音），提取失败静默。**每章写完跑章检时即拦截**——v3 事故形态（ch61 正文说 ch62 招牌句、ch62 说 ch63 锚句）在当章章检当场出声，不必等下一份复评报告。

* 边界声明：只能查「已声明」的签名句（跨批写作时未来章细纲未出则查不到提前释放），未声明的招牌句靠三查③人工走查——advisory 宁报不拦，机械与人工各守一半。

**K3｜成稿剥离门禁**（落点：新脚本 `guyin-check-strip.js`；治 G3/S1）

* 正文文件结构契约：**只允许** **`## 第N章：标题`** **一个标题**，无小节标题、无「承接」段、无任何工序标记。检查项：
